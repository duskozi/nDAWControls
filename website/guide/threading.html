Threading and real-time data

How to get levels, MIDI activity and the song position from your audio or MIDI thread onto the screen without stutter.

#The rule

WPF controls belong to the UI thread. Audio callbacks, MIDI input and sequencer timers run on other threads. Some nDAWControls methods are made to be called from those threads directly; everything else (properties, most methods) must be called on the UI thread, as with any WPF control.

#Which methods are thread-safe

Any thread (lock-free)UI thread only
LevelMeter.PushLevels
ChannelStrip.PushLevels
MidiActivityMonitor.NoteOn / NoteOff / ControlChange / PitchBend / ProgramChange / ChannelPressure / PolyPressure / AllNotesOff / ProcessMessage / ProcessShortMessage		 Every dependency property (Value, Position, CurrentStep, PlayheadPosition …)
PianoKeyboard.SetHighlighted / SetState
PianoPedals.ApplyControlChange
TrackHeader.NoteOn / NoteOff
MidiActivityMonitor.Reset

The thread-safe methods only store the newest values. The control picks them up once per frame on the UI thread, so calling them a thousand times a second costs almost nothing and never blocks your audio.

#Feeding meters from the audio thread

C#
// Called by your audio engine for every block, on the audio thread.
void ProcessBlock(ReadOnlySpan<float> left, ReadOnlySpan<float> right)
{
    float pl = 0, pr = 0, sl = 0, sr = 0;
    for (int i = 0; i < left.Length; i++)
    {
        float l = Math.Abs(left[i]), r = Math.Abs(right[i]);
        if (l > pl) pl = l;
        if (r > pr) pr = r;
        sl += l * l; sr += r * r;
    }
    strip.PushLevels(pl, MathF.Sqrt(sl / left.Length), pr, MathF.Sqrt(sr / right.Length));
}

Keep a reference to the control (or to an interface around it) in your engine. Don't use Dispatcher.Invoke from the audio thread: it blocks until the UI thread is free, which causes dropouts.

#Showing the playhead

Positions change every frame during playback. The smoothest way is to read your engine's clock in CompositionTarget.Rendering, which WPF raises once per frame on the UI thread:

C#
CompositionTarget.Rendering += OnFrame;

void OnFrame(object? sender, EventArgs e)
{
    double beats = engine.PositionInBeats;      // read a volatile field, no lock
    transport.Position     = beats;
    roll.PlayheadPosition  = beats;
    steps.CurrentStep      = engine.IsPlaying ? (int)(beats * 4) % 16 : -1;
}

// Unsubscribe when the window closes.
Closed += (s, e) => CompositionTarget.Rendering -= OnFrame;

#MIDI input

MIDI input callbacks come on a driver thread. Send activity straight to the monitor, and marshal everything else to the UI thread with Dispatcher.BeginInvoke (never Invoke):

C#
void OnMidiIn(int status, int data1, int data2)       // MIDI driver thread
{
    activity.ProcessMessage(status, data1, data2);    // thread-safe

    int type = status & 0xF0;
    if (type == 0x90 && data2 > 0)
        Dispatcher.BeginInvoke(() => keys.SetHighlighted(data1, data2));
    else if (type == 0x80 || type == 0x90)
        Dispatcher.BeginInvoke(() => keys.SetHighlighted(data1, false));
    else if (type == 0xB0)
        Dispatcher.BeginInvoke(() => pedals.ApplyControlChange(data1, data2));
}

#Hidden parts cost nothing

Meters and activity lights only draw while they are visible. Put optional parts of your UI in a DawPanel (or set Visibility="Collapsed"), and a hidden mixer or monitor uses no CPU, even if your engine keeps pushing levels.
